## What each capture is for

- **`baseline_modbus.pcap`** — the "normal" side of the picture: one master
  polling one PLC with reads only. It is the benign capture the IDS is expected
  to stay quiet on, and it is what `dpi:drift` fires on.
- **`modbus_recon_fanout.pcap`** — read-only enumeration: a single host
  addressing three distinct control assets in fourteen seconds. The DPI profiler
  asserts **T0888 (Remote System Information Discovery)** on it. No Suricata rule
  fires. That is not a detection failure: the Suricata ruleset covers control
  writes, and read-only fan-out is covered one layer up by the `Modbus Control
  Asset Enumeration` correlation rule in `ot-detection-engineering`, which counts
  distinct destinations per source inside a five-minute window. This capture is
  the evidence that motivated that rule.
- **`setpoint_write.pcap`** — the control write: a supervisory host that is not
  an allowlisted control writer writes a setpoint-class register, outside any
  approved change window. This is the capture that exercises the whole path —
  DPI classification, asset-context enrichment, the CRITICAL report, and the
  Suricata rule.
- **`setpoint_write_maintenance.pcap`** — the same class of operation from the
  same source, inside an approved maintenance window. The same rule fires and the
  same techniques are derived, so the only thing that differs between the two
  write captures is context. That is the point: the report for this one is HIGH,
  not CRITICAL, because `automation/change_windows.json` covers the event time.

## Known limitations (read this before quoting the captures)

**The two older captures are not valid TCP conversations.** Every packet in
`baseline_modbus.pcap` and `modbus_recon_fanout.pcap` is a SYN sent from source
port 20, with the Modbus payload carried on the SYN; the PLC answers with a RST
(`baseline_modbus.pcap` only). No handshake completes, so no flow is ever
established and no `flow:to_server,established` Suricata rule can match them,
whatever they contain. They exercise the DPI profiler, which reads
application-layer fields, and nothing else.

This is why the earlier demo needed `--trigger-alert` to produce a report, and
why a rule cannot have fired on `modbus_recon_fanout.pcap`. Both write captures
were built with a full handshake for exactly this reason.

**`modbus_recon_fanout.pcap` was previously named `modbus_attack_lateral.pcap`.**
The rename is deliberate: three read requests from one host to three PLCs is
enumeration, not lateral movement, and the old name invited a claim the bytes do
not support.

**`172.21.0.1` is not in `automation/asset_inventory.json`.** The baseline master
is therefore reported as an unknown asset, which is why `dpi:drift` scores zero
on actionability in `metrics/detection-quality.md`. That is an honest gap: the
poller is unmanaged in the asset model.

## Provenance

Both write captures are generated by `pcaps/generate_setpoint_write.py` (Scapy),
which documents the addressing, the register, the values and the two timelines.
The output is deterministic: regenerating produces the same bytes and the same
hashes. The two older captures were captured in the lab environment and are kept
byte-identical to what Malcolm ingested, so the dashboard screenshots in
`dashboards-and-visibility/` still describe them.

`automation/ingest_audit.log` is re-baselined whenever the committed captures or
the audit schema change, so that every line is producible by the current code and
maps to a capture above. It has been re-baselined twice: once on 2026-09-21 to
drop entries for a capture that was never committed, and once when the triage
loop added the `trigger` and `detections` fields the quality metric joins on.
Both are recorded here rather than hidden. The writer itself is append-only.

## Regenerating

```bash
python3 pcaps/generate_setpoint_write.py          # rewrite both write captures
python3 detection-engineering/suricata_check.py   # refresh alert evidence (docker)

export MALCOLM_PCAP_DIR=/tmp/malcolm-pcap
python3 automation/malcolm_ingest.py --file baseline_modbus.pcap --trigger-alert
python3 automation/malcolm_ingest.py --file modbus_recon_fanout.pcap --trigger-alert
python3 automation/malcolm_ingest.py --alerts detection-engineering/evidence/setpoint_write.json
python3 automation/malcolm_ingest.py --alerts detection-engineering/evidence/setpoint_write_maintenance.json
python3 automation/detection_quality.py           # refresh the metric
```

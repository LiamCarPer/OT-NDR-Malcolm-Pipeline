the pipeline makes is reproducible without a plant. Hashes below are the

## What each capture is for

- **`baseline_modbus.pcap`** — the "normal" side of the picture: one master
  polling one PLC with reads only. It is the benign capture the IDS is expected
  to stay quiet on.
- **`modbus_recon_fanout.pcap`** — read-only enumeration: a single host
  addressing three distinct control assets in fourteen seconds. The DPI profiler
  asserts **T0888 (Remote System Information Discovery)** on it. No Suricata rule
  fires,
  which is a real coverage gap rather than a success: the ruleset has no
  read-enumeration detection.
- **`setpoint_write.pcap`** — the control write: a supervisory host that is not
  an allowlisted control writer writes a setpoint-class register. This is the
  capture that exercises the whole path — DPI classification, asset-context
  enrichment, the CRITICAL report, and the Suricata rule.

## Known limitations (read this before quoting the captures)

**The two older captures are not valid TCP conversations.** Every packet in
`baseline_modbus.pcap` and `modbus_recon_fanout.pcap` is a SYN sent from source
port 20, with the Modbus payload carried on the SYN; the PLC answers with a RST
(`baseline_modbus.pcap` only). No handshake completes, so no flow is ever
established and no `flow:to_server,established` Suricata rule can match them,
whatever they contain. They exercise the DPI profiler, which reads
application-layer fields, and nothing else.

This is why the earlier demo needed `--trigger-alert` to produce a report, and
why a rule cannot have fired on `modbus_recon_fanout.pcap`.
`setpoint_write.pcap` was built with a full handshake for exactly this reason.

**`modbus_recon_fanout.pcap` was previously named `modbus_attack_lateral.pcap`.**
The rename is deliberate: three read requests from one host to three PLCs is
enumeration, not lateral movement, and the old name invited a claim the bytes do
not support.

**`172.21.0.1` is not in `automation/asset_inventory.json`.** The baseline master
is therefore reported as an unknown asset. That is an honest gap: the poller is
unmanaged in the asset model.

## Provenance

`setpoint_write.pcap` is generated by `pcaps/generate_setpoint_write.py`
(Scapy), which documents the addressing, the register, and the timeline. The
other two were captured in the lab environment and are kept byte-identical to
what Malcolm ingested, so the dashboard screenshots in
`dashboards-and-visibility/` still describe them.

`automation/ingest_audit.log` was re-baselined on 2026-09-21: it previously
carried entries for local runs against a capture (`setpoint_attack.pcap`) that
was never committed and no longer exists. Every line in the log now maps to one
of the three captures above. The writer is append-only; only that one
re-baseline was manual, and it is recorded here rather than hidden.

## Regenerating

```bash
python3 pcaps/generate_setpoint_write.py          # rewrite the write capture
MALCOLM_PCAP_DIR=/tmp/malcolm-pcap python3 automation/malcolm_ingest.py --all --trigger-alert
python3 detection-engineering/suricata_check.py   # requires docker and the ruleset
```
